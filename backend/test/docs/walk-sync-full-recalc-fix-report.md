# 微信步数同步后累计步行积分修复报告（同步即全量重算）

## 问题现象

用户点击「同步微信步数」后，积分明细里能看到前几天的运动步数，但「我的」页面累计运动步数已达 2000 多步（如 2611 步），累计步行积分仍只有 1 分。按规则应先汇总全部有效运动步数再整除：`walking_points = total_steps // 1000`，2611 步应为 2 分。

## 根因（两层）

### 1. 同步链路只重算本次写入日期起，历史错账不修复

- `sport_service.sync_today` 写入步数后只调用 `sync_walk_from(db, user_id, min(processed))`——仅从本次同步最早日期起重算台账，该日期之前的旧口径错账（017 迁移按「每日各自取整」回填的 walk 行）不会被修正；
- 4afccdd 加了「启动时全量修复」，但依赖后端重启，用户同步时依旧得不到正确积分，且不符合「同步后由后端保证重算」的要求。

### 2. 部署库从未执行 019/020 结构迁移

- 生产库 `schema_migrations` 仅记录到 018：`daily_sport` 缺 `source`/`synced_at`/`sync_status` 三列（019），`questions` 缺 `active` 列（020）；
- 新后端代码部署后，同步写 `daily_sport` 会因缺列直接 500（ORM INSERT 带 source 列），修复无法落地。

## 修复内容

### 代码（backend）

- `points_service.py`
  - 新增 `recompute_walk(db, user_id)`：按运动源数据全量核对并修复单个用户全部步行台账（与启动 `recompute_walk_all` 共用 `_verify_batch` 实现），覆盖旧口径错账、补建缺失行、清零无运动记录的残留行，保证累计步行积分恒等于 `累计计分步数 // 1000`；
  - 删除仅增量重算的 `sync_walk_from`（不再被调用），`_capped_sum` 去掉不再使用的 `before_date` 参数；
  - 模块 docstring 与相关注释同步新口径。
- `sport_service.py`
  - `sync_today`：写入 7 日数据后调用 `points_service.recompute_walk(db, user_id)` 全量修复（在提交前、同一事务内），并保留启动时全量修复兜底；`add_steps`（手动补步）同样改为全量修复。
- 文档：`backend/design.md`、`backend/README.md` 积分规则与 service 职责说明同步。

### 数据库（生产 openGauss）

- 通过 `docker compose -f docker/compose.yml up database-init` 补执行 019（结余口径重算 + `daily_sport` 三列）与 020（`questions.active`），脚本幂等，未改动任何既有业务数据；
- 迁移后复核：`schema_migrations` 记录 019/020，93 行存量运动记录 `source` 回填 `werun`，全库逐用户步行台账与结余口径理论 0 不一致。

## 修改后的积分计算逻辑

```text
累计步行积分 = 累计计分步数 // 1000（向下取整）
累计计分步数 = Σ min(每日步数, 20000)，每日最多 20000 步参与累计（保留既有每日上限）
逐日台账 = floor(至当日累计 / 1000) - floor(前一日累计 / 1000)（跨日零头结余，供积分明细展示）
```

同步/补步/启动修复三处均按 `daily_sport` 源数据全量核对修复，幂等；`total = walk + quiz`；旧 `legacy` 流水不计入。
