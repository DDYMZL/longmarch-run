# .env.prod

## 1. 文件路径
`admin/.env.prod`（实测 4 行）

## 2. 文件职责
管理后台**生产/联调环境**的环境变量文件。仅在 Vite mode 为 `prod` 时加载，对应 `npm run dev:prod` 与 `npm run build` 两条命令（`admin/package.json:8-9`）。其中的 `VITE_API_PROXY` 供 `admin/vite.config.ts:13` 作为 dev server `/api` 代理的上游地址，当前约定为**指向远程已部署后端**。

> **本文档只记录配置项名称、行号与用途，不复制任何实际值**（`.qoder/README.md` §3.14、§4「敏感配置」行）。

## 3. 业务需求
- **本地以生产后端为上游做联调**：这是本文件**唯一的实际用途**。`:2-3` 的注释已明确写清——「`vite build` 不启用 dev server proxy，此处的 `VITE_API_PROXY` 仅对 `dev:prod` 生效，让本地以生产后端为上游进行联调；正式部署时 `/api` 由 nginx 反代到后端」。即：需要在本地浏览器里用真实生产数据复现问题时，跑 `npm run dev:prod`，不必把整个后端搬到本机。
- **与构建 mode 对齐**：`761d860`（2026-10-16）同时把 `build` 改为 `vite build --mode prod`，使「构建产物对应的环境」与「本文件」在语义上配对。`docs/迭代记录.md` 的 `761d860` 条目进一步说明：该模式下 `VITE_API_PROXY` 实际由部署侧 nginx 反代 `/api` 承担，`--mode prod` 主要是为了语义一致并与 `dev:prod` 共用同一份 env。
- **命名与后端保持一致**：文件名取 `.env.prod` 而非 Vite 默认的 `.env.production`，是为了与 `backend/.env.prod` 对齐（后端由 `APP_ENV=prod` 选择该文件，见 `.qoder/backend/.env.prod.md`）。代价是必须靠 `--mode prod` 显式指定，见 §8。
- **入库状态**：本文件**已被 git 跟踪**（`git ls-files admin` 实测命中）。根 `.gitignore` 的 `.env` 模式只匹配名为 `.env` 的文件、`.gitignore:12` 的 `.env*.local` 只匹配 `.local` 后缀，故不在忽略范围内。`.qoder/PROJECT.md` §9「已被 git 跟踪（入库）」将其敏感度评为**低：仅 API 代理地址，无凭据**。

## 4. 核心功能

### 4.1 文件结构
共 4 行：3 行注释（`:1-3`）+ 1 个配置项（`:4`）。`KEY=VALUE` 形式，无分节标题、无引号、无 `export` 前缀。

| 行 | 内容类型 | 说明 |
|---|---|---|
| `:1` | 注释 | 标明生效命令：`npm run build` 与 `npm run dev:prod` |
| `:2-3` | 注释（跨两行） | 关键警示：`vite build` 不启用 dev proxy，本项**仅对 `dev:prod` 生效**；正式部署时 `/api` 由 nginx 反代 |
| `:4` | 配置项 | `VITE_API_PROXY` |

`:2-3` 是全套 admin 工程配置里最重要的一段自解释文档：它当场否掉了「改这个值就能改生产接口地址」的常见误解。

### 4.2 配置项清单

| # | 行号 | 配置项 | 用途 | 生效命令 | 敏感性 |
|---|---|---|---|---|---|
| 1 | `:4` | `VITE_API_PROXY` | Vite dev server `/api` 代理的**上游后端基地址**（协议 + 主机 + 可选端口，不含路径）。当前指向**远程已部署后端**（HTTPS 域名，走默认 443，接口路径由 `/api` 前缀承担） | **仅 `npm run dev:prod`**（`admin/package.json:8`）。`npm run build` 虽也加载本文件，但构建产物不含代理配置，故此项对产物**无影响** | **非机密**：只是域名地址，不含账号/口令/密钥/Token。仍按规则不抄原值 |

**这是本文件唯一的配置项**，键集与 `admin/.env.development` 完全相同，差异只在值的语义（远程 vs 本地）。

### 4.3 三条命令下的实际效果对照
| 命令 | Vite mode | 加载的 env 文件 | `VITE_API_PROXY` 的实际作用 |
|---|---|---|---|
| `npm run dev`（`admin/package.json:7`） | `development` | `admin/.env.development` | 代理到本地后端 |
| `npm run dev:prod`（`:8`） | `prod` | **本文件** | 代理到远程后端——**本文件唯一真正生效的场景** |
| `npm run build`（`:9`） | `prod` | **本文件** | **无作用**：`vite build` 不启动 dev server，`admin/vite.config.ts:8-18` 的 `server` 段整体不参与打包；且 `admin/src` 内实测无任何 `import.meta.env` 使用，该值也不会被注入产物 |
| `npm run preview`（`:11`） | `production` | **不加载本文件**（仓库内无 `.env.production`） | 回退 `admin/vite.config.ts:13` 的本地默认值 |

## 5. 输入与输出
- **输入格式**：纯文本 `KEY=VALUE`，Vite 内部用 dotenv 解析；`#` 起行为注释；值无需引号。
- **被谁读取、何时读取**
  | 读取方 | 时机 |
  |---|---|
  | `admin/vite.config.ts:5` 的 `loadEnv(mode, '.', '')` | 执行 `vite --mode prod` / `vite build --mode prod` 时，在配置求值阶段读取。第三参为空串 → 不按 `VITE_` 前缀过滤 |
  | Vite 自身的 env 注入机制 | 只注入 `VITE_` 前缀变量到客户端代码；但 `admin/src` 内**无 `import.meta.env` 消费点**，故本文件的值不会进入 `admin/dist/` 的任何 JS |
- **加载优先级**（Vite 标准行为）：`.env.prod.local` > `.env.prod`（本文件）> `.env`。仓库内**不存在** `admin/.env`；`.env.prod.local` 被 `.gitignore:12` 的 `.env*.local` 忽略，属本机私有覆盖，**不建档**（`.qoder/README.md` §4「本机私有配置」行）。
- **输出**：无产物。对 `dev:prod` 而言，输出是「5173 端口的 dev server + `/api` 转发到远程后端」的运行态；对 `build` 而言，本文件不产生任何可观测输出。
- **异常形态**：值不可达 → `dev:prod` 下代理返回 502/ECONNREFUSED；远程为 HTTPS 时若缺 `changeOrigin: true`（`admin/vite.config.ts:14` 已配）会因 `Host` 头失配而握手失败；文件缺失 → 静默回退 `admin/vite.config.ts:13` 的本地默认值，表现为「以为连的是生产、其实连的本机」。

## 6. 依赖关系
**依赖的外部资源**
- 远程已部署后端：HTTPS 域名 + nginx 反代 `/api` → 本机后端进程（`.qoder/ARCHITECTURE.md` §12）。生产由 systemd 服务 `longmarch-backend` 托管、`APP_ENV=prod`（`.qoder/PROJECT.md` §10 待确认清单第 2 条已查证部分）。
- 远程后端的配置由 `backend/.env.prod` 承载，与本文件**同名后缀、不同职责**：本文件只影响本地 Vite 代理，后端那份才决定生产运行参数。

**必须与哪些文件保持一致**
| 文件 | 一致性要求 |
|---|---|
| `admin/package.json:8-9` | `dev:prod` 与 `build` 必须带 `--mode prod`；漏写或写成 `--mode production` 都会让本文件不被加载 |
| `admin/vite.config.ts:13-15` | 键名必须是 `VITE_API_PROXY`；`changeOrigin: true` 对 HTTPS 上游是必需的；`ws: true` 保证 `admin/src/utils/liveUpdates.ts:61-62` 的 `/api/ws/updates` 在 `dev:prod` 下也能连（远程 nginx 侧还需转发 `Upgrade`/`Connection` 头，见 `.qoder/ARCHITECTURE.md` §12） |
| `admin/.env.development` | 键集保持一致（当前均为单键）；两份文件构成「本地 / 远程」二元约定，任一侧新增键都需评估另一侧 |
| `admin/src/api/request.ts:14-17` | `baseURL: '/api'` 是相对路径，因此本文件的值**只写主机部分、不得带 `/api` 后缀** |
| nginx（生产，配置不在仓库内） | 正式部署时 `/api` 由 nginx 反代，本文件不参与；nginx 还需为 HTML5 history 模式配 SPA 回退（`admin/src/router/index.ts:98`），已记为 `.qoder/ARCHITECTURE.md` §16「待确认清单」第 1 项 |
| `backend/.env.prod` | 命名约定对齐（均为 `.env.prod`）；但两者**不共享任何键**，改动互不影响 |

## 7. 业务规则
无——本文件只承载配置项，不含积分、权限、状态流转等业务规则。它承载的**工程约定**：

1. **`build` 与本文件是「语义配对」而非「功能依赖」**：`--mode prod` 让构建读取本文件，但本文件的唯一键对产物无影响。真正的生产接口寻址由 nginx 反代承担（`:2-3` 注释即为防止误解而写）。
2. **联调走 `dev:prod`，不改 `dev`**：需要生产数据时执行 `npm run dev:prod`，而不是把 `admin/.env.development` 改成远程地址——后者会污染入库文件并破坏「一命令一环境」约定。
3. **本文件的值不进入构建产物**：`admin/src` 内无 `import.meta.env` 消费点，且 `server.proxy` 不参与打包，故 `admin/dist.zip` 中不含任何后端主机名。

## 8. 修改约束
- **文件名 `.env.prod` 不是 `.env.production`——这是本项目最容易踩的坑**：Vite 对 production 模式的**默认**文件名是 `.env.production`，本文件之所以生效，完全依赖 `admin/package.json:8-9` 显式传入 `--mode prod`。因此：
  - **不要**把本文件「规范化」重命名为 `.env.production`——改名后 `dev:prod`/`build` 的 `--mode prod` 会找不到它，静默回退本地默认上游；
  - **不要**去掉 `admin/package.json` 里的 `--mode prod`；
  - **不要**新增 `npm run preview -- --mode production` 之类的命令并期望它读本文件（`preview` 默认 mode 是 `production`，与本文件名不匹配）；
  - 命名与 `backend/.env.prod` 保持一致，跨端改名须两端同步。
- **禁止写入任何凭据**：本文件已入 git 历史，写入的值会永久留存。经 `git log -p -- admin/.env.prod` 核对，自 `761d860` 创建以来**只出现过 `VITE_API_PROXY` 一个键**，从未写入口令、密钥、Token 或连接串——该干净状态需保持。生产凭据一律放 `backend/.env.prod`（服务器侧），**不得**出现在前端工程配置里。
- **凡 `VITE_` 前缀的变量都视为公开**：`envPrefix` 未修改（`admin/vite.config.ts` 无该项），`VITE_*` 会被注入客户端产物。当前 `admin/src` 无消费点故未注入，但一旦有人加了 `import.meta.env.VITE_XXX`，本文件里的值就会出现在 `admin/dist/` 的 JS 中。新增键前必须先确认它可公开。
- **值只写「协议 + 主机 + 可选端口」，不带路径**：`/api` 前缀由 `admin/vite.config.ts:12` 与 `admin/src/api/request.ts:15` 承担。
- **改本文件不影响生产运行**：不要把它当成「生产配置」去改数据库地址、密钥等——那些在 `backend/.env.prod`。本文件的作用域仅限「本地 Vite dev server 的代理上游」。
- **`:2-3` 的警示注释不可删**：它是防止「以为改这里就改了生产接口地址」的唯一现场说明。
- **临时改用别的上游请建 `.env.prod.local`**（已被 `.gitignore:12` 忽略、不建档），不要直接改本文件后忘记改回。

- 与 `admin/package.json:8-9` 的 `--mode prod`、`admin/vite.config.ts:5,13` 的读取链路自洽；`761d860` 的提交说明与 `docs/迭代记录.md` 的 `761d860` 条目均确认此约定。

- 注释质量高：`:2-3` 主动澄清了「build 时此项不生效、生产由 nginx 反代」，与 `.qoder/ARCHITECTURE.md` §12 的部署描述一致。

**已知问题 / 风险（事实性陈述）**
1. **文件名与 Vite 默认约定不符**（`.env.prod` vs `.env.production`）：功能上靠 `--mode prod` 兜住，但对不熟悉本项目的人构成认知陷阱；`npm run preview`（mode 为 `production`）因此读不到本文件，预览时代理会回退到本地默认上游。这是有意为之（与 `backend/.env.prod` 对齐）还是历史遗留——从 `761d860` 的提交说明看是**有意为之**，但仓库内未见 ADR 记录（`.qoder/decisions/` 只有 README 索引）。
2. **`build` 加载本文件却不使用其中任何值**：`--mode prod` 对构建的实际影响仅在于「读哪份 env」，而该 env 的唯一键对产物无作用。属**语义正确但功能空转**，容易让人误以为构建产物与后端地址绑定。`:2-3` 的注释已作澄清。
3. **无 `.env.production` 兜底**：任何以默认 `production` mode 运行的命令（`vite build` 不带 `--mode`、`vite preview`）都读不到本文件，且因 `admin/vite.config.ts:13` 有 `||` 回退而**静默**连到本地后端。
4. **远程上游的 WebSocket 依赖 nginx 正确转发升级头**：`dev:prod` 下 WS 走 `admin/vite.config.ts:15` 的 `ws: true`，但远程侧 nginx 若未转发 `Upgrade`/`Connection`、未用 `proxy_http_version 1.1`，实时推送会不通——`.qoder/ARCHITECTURE.md` §12 已记录此根因；nginx 配置文件不在仓库内、服务器路径未核实（`.qoder/ARCHITECTURE.md` §16 待确认清单第 2 条）。
5. **本文件不受任何自动化校验**：不在 tsconfig 的 `include` 内、无 lint、无 schema 校验。

**待确认**
- `npm run dev:prod` 是否能真正打通远程后端（含 WS）——按任务约束**未执行** `npm run dev:prod`、未连接远程主机，仅静态核对；最近一次远程端到端实测见 `docs/迭代记录.md` 的 `527db98` 条目（当时远程地址写在 `.env.development` 中，`761d860` 才迁到本文件）。
- 生产 nginx 的 `/api` 反代与 SPA 回退实际配置（不在仓库内）。
- 是否应补一份 `.env.production`（或把 `preview` 脚本加上 `--mode prod`）以消除 §9.3 的静默回退——**待确认**（属团队取舍，本次未做任何修改）。
