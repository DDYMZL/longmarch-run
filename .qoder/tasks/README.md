## 2. 新任务记录的模板（9 项，缺一不可）

```markdown
# <任务标题>

- **日期**：YYYY-MM-DD
- **状态**：进行中 / 已完成 / 已回滚
- **关联提交**：`xxxxxxx`（完成后填）
- **关联文档**：`.qoder/CHANGELOG.md` §2.x、`docs/迭代记录.md` 对应条目

## 1. 需求背景
为什么做这件事：业务动因、缺陷现象、外部约束、提出人/来源。

## 2. 修改前的行为
当前代码实际是怎么做的（附 `文件:行号`）。**必须实测确认，不得凭文件名推断。**

## 3. 期望行为及验收标准
逐条列出可验证的验收项，每条都要能被测试或浏览器验收覆盖。

## 4. 影响文件清单
| 文件 | 改动类型（新增/修改/删除） | 说明 |
| --- | --- | --- |

## 5. 实施方案
分步骤说明；有多个可选方案时列出取舍理由（或另建 `.qoder/decisions/` 记录）。

## 6. 实际修改记录
**实施后回填**，与第 5 项的方案偏差要写明原因。

## 7. 数据库或接口变更
- 数据库：迁移编号、表/列变化、是否含数据回填、**是否可重跑**
- 接口：端点、请求/响应字段、状态码、响应头
- 若无变更，明确写「无」

## 8. 测试结果
脚本编号 + 通过情况（如 `s20` 25/25）、报告路径、浏览器验收用例编号与截图。

## 9. 发布与回滚说明
- 发布顺序（迁移先于代码？前后端谁先？）
- 回滚步骤与回滚后数据状态
- 是否需要清理缓存 / 强制刷新前端
- 部署情况无仓库内证据时写 **待确认**
```

## 3. 建档时机

| 情形 | 是否建任务记录 |
|---|---|
| 涉及数据库迁移 | **必须建** |
| 涉及破坏性/不可逆变更（数据回填、口径重定义、令牌语义变更） | **必须建** |
| 跨三端（backend + frontend + admin）的联动变更 | **必须建** |
| 缺陷修复且根因非显而易见（如误诊后更正） | **必须建** |
| 单文件小改动、纯文档、纯样式 | 不建，只在 `docs/迭代记录.md` 追加一条 + 更新对应文件的 `.qoder/**.md` §10 迭代记录 |

**任务记录与文件级文档的分工**：任务记录讲「这一次为什么这么改」，文件级文档 §10 迭代记录讲「这个文件被改过哪些次」。两者互相引用，不互相替代。
