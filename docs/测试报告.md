## 7. Bug 清单

### Bug#1 管理后台新建组织必失败（HTTP 500）

- **编号**：BUG-001
- **标题**：管理后台新建组织必失败（organizations 表主键无自增序列）
- **严重程度**：高（组织架构管理核心功能完全不可用）
- **模块**：后端（数据库 DDL）+ 管理后台前端（异常处理）
- **测试入口**：admin 组织架构页「新增顶级组织/新增下级」；API `POST /api/admin/orgs`
- **前置条件**：无（admin 登录即可）
- **复现步骤**：
  1. 登录管理后台，进入「组织架构」页；
  2. 点击「新增顶级组织」，输入名称（如「E2E测试组织」），点击「保存」；
  3. 观察网络请求与页面表现。
- **实际结果**：`POST /api/admin/orgs` 返回 **500 Internal Server Error**；浏览器控制台报 `Failed to load resource: 500` 与 `Unhandled error during execution of component event handler`（保存事件处理器抛未捕获异常）；弹窗保持打开、**无任何用户友好错误提示**。
- **预期结果**：新建成功，列表出现新组织。
- **涉及接口/数据**：`POST /api/admin/orgs`；`organizations` 表。
- **初步定位**：`docker/init/001_schema.sql` 中 `organizations` 表 `id INTEGER PRIMARY KEY` **无 SERIAL/自增**（对比 `users` 表 `id SERIAL PRIMARY KEY`）；ORM `models.py` 中 `Organization.id` 为 `Integer, primary_key=True`，插入时未指定 id 即向 openGauss 插入 NULL 主键而报错。修复方向（仅定位，未实施）：DDL 迁移为自增（IDENTITY/SERIAL）+ 迁移登记，或建表时指定序列。
- **能否稳定复现**：是（API 与 UI 两层均稳定复现）
- **日志**：浏览器 console `msgid=47/48`；网络请求 `reqid=282 POST /api/admin/orgs [500]`
- **截图证据**：浏览器实测弹窗截图（会话内取证）；e2e 结果 `D11 actual=500 detail=Internal Server Error`

### Bug#2 答题提交接口接受非当日抽题题目并计分

- **编号**：BUG-002
- **标题**：答题提交接口接受非当日抽题题目并计分（可伪造满分）
- **严重程度**：中（积分/成就体系可被绕过）
- **模块**：后端（业务规则校验缺失）
- **测试入口**：API `POST /api/quiz/submit`
- **前置条件**：用户已登录且当日未提交过答卷
- **复现步骤**：
  1. 获取今日抽题（`GET /api/quiz/daily`，5 题）；
  2. 用**不在今日题目列表中的 question_id**（如 id=9）构造答案提交 `POST /api/quiz/submit`；
  3. 观察返回得分与积分。
- **实际结果**：提交被接受，非当日题目按提交答案判分并计分（如 1 题答对得 20 分、+5 积分）。
- **预期结果**：拒绝非当日抽题题目（400），或按无效提交处理不计分。
- **涉及接口/数据**：`POST /api/quiz/submit`；`quiz_records`、积分记录。
- **初步定位**：`backend/app/services/quiz_service.py` submit 仅校验「当日是否已提交」，对 answers 中的 question_id 与当日抽题集合**不做比对**，直接按全题库答案映射判分。修复方向：校验每个 question_id 必须属于当日 `daily_questions` 缓存表。
- **能否稳定复现**：是（e2e E10 稳定复现，actual 20 分/expected 0 分）
- **日志**：e2e 结果 E10 detail：`{totalCount:1, correctCount:1, score:20, points:5}`

### Bug#3 手动补步接口无下限校验，负数补步使步数为负

- **编号**：BUG-003
- **标题**：手动补步接口无下限校验，负数补步使步数为负
- **严重程度**：中（数据完整性；负步数污染排行榜/统计/达标判定）
- **模块**：后端（入参校验缺失）
- **测试入口**：API `POST /api/sport/add`
- **前置条件**：用户已登录
- **复现步骤**：
  1. `POST /api/sport/add`，body `{"delta": -100000}`；
  2. 查询今日步数（`GET /api/sport/today`）与排行榜。
- **实际结果**：请求 200 成功，步数从 4,885 变为 **-95,115**；负步数进入 `daily_sport`，污染累计步数统计与排行榜。
- **预期结果**：负数被 422 拒绝（或至少步数不为负）。
- **涉及接口/数据**：`POST /api/sport/add`；`daily_sport.steps`。
- **初步定位**：`backend/app/schemas/schemas.py` 中 `AddStepsRequest.delta: int = 0` **无 `ge=0` 约束**，`sport_service.add_steps` 直接叠加。修复方向：schema 加 `Field(ge=0)`。
- **能否稳定复现**：是（e2e E12 稳定复现，steps 4885 → -95115）
- **日志**：e2e 结果 E12 detail：`steps0=4885 -> steps1=-95115`
- **备注**：复现脚本残留的负步数（测试用户 id 248/249 各约 -95,000 步）已污染测试环境总步数统计（本报告第 6 章驾驶舱数据 125,443 中已含该污染）；该污染属测试过程产物、非产品行为，测试结束后可清理。

### Bug#4 管理后台驾驶舱收到 WS 实时动态后渲染崩溃、页面数据冻结

- **编号**：BUG-004
- **标题**：驾驶舱 WS 实时动态时间戳格式与 REST 不一致导致渲染崩溃，页面数据冻结
- **严重程度**：高（管理后台核心实时联动功能失效，且页面进入持续报错状态）
- **模块**：管理后台前端 + 后端 WS 数据映射（前后端契约不一致）
- **测试入口**：admin 驾驶舱页（已登录）
- **前置条件**：admin 登录并停留在驾驶舱页；小程序侧任意用户产生写操作（登录/同步步数/答题等）
- **复现步骤**：
  1. 登录管理后台进入驾驶舱，数据正常（如 17 人/120,532 步）；
  2. 通过 API 触发小程序新用户登录 + 步数同步（产生 LOGIN/FIRST_STEP 等 activity 与 data_changed 广播）；
  3. 等待 1-2 秒观察页面与浏览器控制台。
- **实际结果**：
  - 参与总人数 17→18 部分更新，但累计总步数、今日运动人数、人均步数、实时动态列表全部冻结在旧值（页面 120,532 步 vs API 实际 128,532 步）；
  - 浏览器控制台循环报错：`[Vue warn]: Unhandled error during execution of render function/component update at <DashboardView>`（单次触发 26 条，持续累积）；
  - 之后任何写入都不再刷新页面；仅手动刷新页面可恢复（刷新后数据正确）。
- **预期结果**：所有指标卡与实时动态随 WS 广播自动刷新。
- **涉及接口/数据**：
  - WS `/api/ws/updates` activity 消息 `at` 字段 = **毫秒数字时间戳**（如 1791448682843，`backend/app/core/ws.py` `_now_ms()`）；
  - REST `GET /api/admin/activities` `event_time` = **ISO 字符串**（如 "2026-10-08T08:42:00.233265"）。
- **初步定位**：`admin/src/utils/liveUpdates.ts` 的 `formatTime` 期望 ISO 字符串；对数字时间戳执行 `new Date("1791448682843Z")` 得到 Invalid Date，`Intl.DateTimeFormat.format` 抛 `RangeError: Invalid time value`（浏览器内已直接复现该异常）；`DashboardView.vue` 模板 `formatTime(item.event_time)` 在插入 WS 实时动态后 render 崩溃，Vue 组件更新中断，后续所有 reactive 刷新均失败 → 页面数据冻结。数据大屏页实时动态正常（不同渲染路径），佐证问题局限在驾驶舱的 WS 动态插入链路。修复方向（仅定位）：后端 `build_activity` 的 `at` 改为 ISO 字符串，或前端 `formatTime` 兼容毫秒数字。
- **能否稳定复现**：是（刷新页面后再次触发写入，控制台自 msgid=35 起再次循环报错，指标再次冻结）
- **日志**：浏览器 console `msgid=7-32`（首次）、`msgid=35-42+`（复现）；WS 握手首次瞬时失败后自动重连成功（`msgid=3`，重连机制正常，非本 Bug 主体）
- **截图证据**：`admin/test/images/e2e-02-dashboard-frozen.png`（页面冻结在 16 人/110,713 步，API 实际 17 人/120,532 步）

按模块分布：后端 3（BUG-001/002/003，其中 BUG-001 根因在数据库 DDL），管理后台前端+前后端映射 1（BUG-004）。

## 9. 前后端联动问题

1. **BUG-004（驾驶舱 WS 时间戳契约不一致）**：后端 WS 广播 `at` 为毫秒数字、REST 为 ISO 字符串，同一字段两种格式，前端按 ISO 处理导致渲染崩溃。这是本轮发现的最典型前后端联动/数据映射问题。
2. **WS data_changed 联动本身正常**：小程序写入 → 后端广播 → 驾驶舱指标刷新链路在 BUG-004 触发前验证通过（新用户登录后总人数 15→16 自动更新）；数据大屏「实时已连接」与实时动态滚动正常。
3. **admin 新建组织 500 后前端异常未处理**（BUG-001 的前端表现）：axios 错误未捕获，事件处理器抛异常，弹窗不关闭且无错误提示，用户体验问题叠加在 500 之上。
4. **小程序 → admin 数据可见性**：登录/同步/答题/点亮节点等写入均能实时或刷新后正确反映在 admin 各页（驾驶舱除 BUG-004 冻结时段外），orgs 人数统计、排行榜 lit_at 均与 DB 一致。

## 10. 数据一致性问题

1. **统计口径核对（无问题）**：驾驶舱/排名洞察/数据大屏的累计步数均取 `daily_sport` 汇总（实测 125,443 三层一致）；排行榜 lit_at 与 `lit_nodes.lit_at` 一致；orgs 树「直属人数/成员总数」与 `users.org_id` 一致；admin 勋章发放数与 `user_medals` 一致（e2e D08）。
2. **BUG-003 引起的污染**：负步数直接写入 `daily_sport`，导致总步数/排行榜被拉低（复现用户各 -95,000 步）。数据层面不一致的根源在入参校验缺失。
3. **BUG-002 引起的统计偏差**：非当日题目计分使 quiz 积分与「每日一套题」业务语义脱钩（答题记录按提交为准）。
4. **BUG-004 引起的展示层不一致**：后端数据已更新而驾驶舱页面冻结在旧值（页面 120,532 vs API 128,532），属展示层数据不一致（页面 → API → DB 三层中「页面层」失效）。
5. **E14 核查**：隐藏勋章未获得时 `conditionDesc` 返回「获得条件暂未公布」，与需求一致，无问题。

## 11. 自动化测试结果

### 11.1 后端 e2e 套件
- `backend/test/e2e_full_flow.py`：175 用例、171 通过；有效失败 3 个（E10/E12/D11），E14 为历史断言问题（已修正断言并独立核查通过）。结果落盘 `backend/test/e2e-full-results.json`。

### 11.2 小程序 automator 套件（ui-test.cjs 1-5 + merge + shots-tour.cjs）

**发现 4 个自动化测试流程问题（非产品 Bug，均不影响产品功能结论）：**

1. **T11-T13 菜单索引过期**：mine 页在 P1 迭代新增「我的档案」「组织选择」两个菜单项后，`ui-test.cjs` phase4 仍按旧索引 `menuItems[1..3]` 取「运动记录/答题记录/勋章」，实际对应「行军日历/组织选择/运动记录」，导致 T11 起导航错页、阶段 4 异常终止。已用临时补验脚本 `e2e-manual-t11t13.cjs` 按当前页面结构（索引 3/4/5）补验：**T11/T12/T13 全部通过**（运动记录 totalSteps=6912 与首页一致；答题记录同日两次作答仅留 1 条；勋章墙 12 枚分组展示、first-step 必得）。
2. **T13 断言字段过期**：medals 页在 P2 迭代由 `medals[]` 改为 `groups[]` 分组结构，脚本断言字段未同步。
3. **T16a/T16b 深链守卫**：产品链路经 console 监控验证**完全正确**——`[REQ] GET /api/quiz/daily → [RES] 401 → [RELAUNCH] /pages/login/login` 依次执行、无任何 TypeError；但 wx.request 回调中发起的第二个 reLaunch 被 IDE 自动化桥挂起（页面栈不变，桥断开后才生效），属模拟器/IDE 环境性问题，稳定复现但非产品缺陷。
4. **IDE 僵尸进程导致截图巡礼大面积失败**：多轮 `cli.bat quit/auto` 循环累积 **13 个僵尸「微信开发者工具.exe」主进程**，导致 `mini.screenshot` 报 `Cannot destructure property 'rawPath' of 't.getPageMetaByWebviewId(...)' as it is null`（巡礼 2/16）；按 ExecutablePath 匹配 PID 全杀后重启，巡礼恢复 **13/16**（剩余 3 个状态因测试用户已绑定组织无法复现「未选组织」流程）。

**套件有效结论**：22/23 断言通过 + 补验 3/3 + 巡礼 13/16；唯一 FAIL 的 T16a 为环境性问题（产品链路证据正确）。

2. **测试数据清理**：BUG-003 复现残留的负步数（测试用户 id 248/249）与多轮测试用户、测试事件仍在库中，报告所述统计值（如 125,443 步）含测试污染；正式验收前建议按「清空业务数据」流程重置。

## 13. 结论

1. **整体**：三端核心业务流程可用——小程序 10 步闭环全链路（登录→组织→运动→路线→答题→排行→勋章→档案）在 API 层 175 用例与 UI 层 automator 套件下基本全部通过；管理后台除组织新建与驾驶舱实时刷新外各页功能正常；后端业务规则（积分去重、节点点亮、勋章、连续行军、事件广播）与设计文档一致。
2. **缺陷**：共发现 **4 个 Bug**（2 高 2 中），全部稳定复现、证据完整：
   - BUG-001 组织表主键无自增 → 管理后台新建组织必 500（DDL 与 ORM 不一致）；
   - BUG-004 WS 实时动态 `at` 毫秒时间戳与 REST ISO 字符串契约不一致 → 驾驶舱渲染崩溃、数据冻结；
   - BUG-002 答题提交不校验题目归属 → 可提交非当日题目计分；
   - BUG-003 补步无下限校验 → 负步数污染统计。
3. **自动化资产健康度**：后端 e2e 套件可靠（3 个真实缺陷全部由它捕获）；小程序 automator 套件存在 2 处断言过期（菜单索引、medals 字段）与 2 处环境性坑（深链导航挂起、IDE 僵尸进程），已在 §11.2 详录，建议后续同步维护。
4. **数据一致性**：除上述缺陷引发的问题外，页面 → API → 数据库三层核对一致；WS data_changed 联动与统计口径均正确。
5. **建议优先级**：BUG-001（管理功能不可用，且为一行 DDL 级别的根因）→ BUG-004（实时联动失效）→ BUG-003（数据污染，需先修校验再清数据）→ BUG-002（业务规则补强）。
