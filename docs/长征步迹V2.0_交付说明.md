## 5. 积分规则与重算机制

### 5.1 规则（配置项见 `backend/app/core/config.py`）

- 步行：`floor(min(当日步数, 20000) / 1000)`，每日上限 20 分（`POINTS_WALK_STEP_CAP`、`POINTS_WALK_STEPS_PER_POINT`）。
- 答题：每答对 1 题 2 分，每日上限 10 分（`POINTS_QUIZ_PER_CORRECT`、`POINTS_QUIZ_DAILY_CAP`）；超时题不得分。
- 总积分 = 步行积分 + 答题积分；登录、达标、点亮（`gainedPoints` 恒为 0）、连续里程碑不再发积分。
- 排名统一按「总积分 → 累计步数 → user_id」排序，小程序与管理端共用 `rank_service`。

### 5.2 台账模型

- 每人每来源每自然日一行，`biz_key = walk:YYYY-MM-DD / quiz:YYYY-MM-DD`，`(user_id, biz_key)` 唯一。
- 业务写入（步数同步/补步、答题判定）在同一事务内行锁并按源数据**重算覆盖**，而非累加，因此重复同步、重复提交天然幂等。
- 步数只增不减取当日最大值；已有记录的往日按微信运动最终步数校正。并发首写由唯一约束兜底，冲突回滚后重试。

### 5.3 核对与修复

- `points_service.recompute_all(db, fix, user_ids)`：按 `RECOMPUTE_BATCH=500` 分批，从 `daily_sport` 与 `quiz_answers`/`quiz_records` 计算应得积分，与台账逐行比对，检出差值、缺失行与多余行。
- 返回 `users / checked_days / mismatches / fixed` 与最多 50 条样例。
- 管理后台「排名洞察 → 积分核对」默认只读检查，确认后才以 `fix=true` 执行修复并写审计 `points.recompute`。
- 现网核对结果：131–132 名用户、111 个用户日，差异 0。

## 6. 活动时间守卫

- 状态由 `activity_service` 按服务器时间实时计算（北京时间）：未发布 / 未开始 / 进行中 / 已结束。
- 两类准入：
  - **可参与**（`require_activity_participation`）：步数同步/补步、答题开题/提交/重置、点亮、勋章检查、组织选择。活动非进行中时返回 403，并带响应头 `X-Activity-Status`。
  - **可查看**（`require_activity_view`）：积分、排行、答题记录、档案等读接口；已结束时按「结束后可查看」配置放行或拒绝。
  - `/medal/list` 在不可参与时只读，不发放勋章。
  - 关闭「访问限制」后全部放行；无 Token 恒返回 401（鉴权优先于活动守卫）。
- 业务日期统一按 UTC+8 计算，不依赖服务器本地时区。
- 小程序处理（`services/request.js`）：
  - GET 读请求收到带 `X-Activity-Status` 的 403 时，`reLaunch` 到活动状态页（3 秒防抖）；
  - POST 写请求只提示错误，不跳转；
  - 首页在活动结束且允许查看时展示结束横幅，其余页面只读可浏览。
- 管理后台：有未保存改动时禁止发布；发布、撤回均需二次确认；倒计时以服务器时间为准。

## 7. 答题防作弊

- 计时只认服务器时间：每题 90 秒，截止后 2 秒宽限（`QUIZ_ANSWER_GRACE_SECONDS`）抵消网络延迟；超过后提交返回 400，题目标记 `timeout` 且不得分。
- 只下发当前已开的题，且不含答案与解析；判定后才返回正确答案与解析。
- 每题只能提交一次：判定与超时都以 `status='answering'` 为条件做条件更新，并发提交、提交与超时竞争时只有一方生效。
- 开题与会话由唯一约束 `(session_id, seq)` 兜底，并发开题只生成一行；开下一题即放弃当前未答题。
- `GET /quiz/daily` 不会开题，但会把已过截止时间的题判为超时，防止「刷新续命」。
- 答题积分与判定在同一事务写入，中途退出已得积分保留。
- 客户端倒计时仅用于展示：以后端返回的剩余毫秒数 `remainingMs` 起算，不依赖手机本地时钟，改本地时间无法延长作答。

## 10. 风险与遗留项

1. **旧联调脚本未改写**：`e2e_full_flow`、`e2e_datasync`、`s3_aggregates` 仍按 V1 口径（整卷提交、点亮发积分、旧流水），运行会失败，需按 V2 契约重写。
2. **登录 502**：s5、s8、s9 依赖旧的首登自动建号，本地配置真实微信凭证后登录返回 502，为 V2 之前已存在的问题。
3. **积分修复路径**：开发库只执行过只读核对（差异为 0），`fix=true` 修复路径由 s20 在 SQLite 覆盖，未在开发库实际执行；生产执行前建议先只读核对并备份 `points_log`。
4. **组织首次选择 UI 路径**：小程序 O01 首次选择流程只在首次运行时覆盖（固定账号已锁定），后续回归依赖后端 s19/s20。
5. **答题宽限窗口**：截止后 2 秒内的提交仍被受理，属设计取舍（抵消网络延迟），理论上存在 2 秒的额外作答时间。
6. **legacy 流水**：旧积分流水保留但不计入总积分，若运营需要展示历史积分须另行说明口径。
7. **小程序活动跳转防抖**：多个读接口同时 403 时依赖 3 秒防抖避免重复跳转，极端弱网下可能出现一次提示后再跳转。
