## 4. 数据库变更方案（迁移 012，未执行，可改写）

```sql
-- 员工名册（员工编号为稳定业务标识）
CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    employee_no VARCHAR(32) NOT NULL,          -- UNIQUE
    name VARCHAR(64) NOT NULL,
    phone VARCHAR(20) NOT NULL,                -- 规范化 11 位大陆手机号；UNIQUE（唯一匹配，杜绝冲突）
    org_id INTEGER NOT NULL REFERENCES organizations (id),
    employment_status VARCHAR(16) NOT NULL DEFAULT 'active',   -- active 在职 / resigned 离职
    access_status VARCHAR(16) NOT NULL DEFAULT 'enabled',      -- enabled 启用 / disabled 停用
    bound_user_id INTEGER REFERENCES users (id),               -- UNIQUE：一员工一微信、一微信一员工
    bound_at TIMESTAMP, last_login_at TIMESTAMP,
    token_version INTEGER NOT NULL DEFAULT 1,   -- 仅后端维护；停用/离职/启用/换绑自增
    import_batch_id VARCHAR(32),                -- 关联 import_previews.token
    disabled_at TIMESTAMP, disabled_by VARCHAR(64), disabled_reason VARCHAR(200),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- uq_employees_no / uq_employees_phone / uq_employees_bound_user；ix_employees_org / 状态

-- 入驻二维码（只引导、不授权）
CREATE TABLE onboarding_qrcodes (
    id SERIAL PRIMARY KEY,
    scene VARCHAR(32) NOT NULL,        -- 'J' + 随机串（≤32 位，getwxacodeunlimit 限制）；UNIQUE
    status VARCHAR(16) NOT NULL DEFAULT 'active',   -- active / revoked
    expires_at TIMESTAMP,              -- NULL = 长期有效（需管理员显式选择）
    created_by VARCHAR(64), created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    revoked_at TIMESTAMP, revoked_by VARCHAR(64)
);

-- 准入策略（单行配置 + 允许组织）
CREATE TABLE access_policy (id INTEGER PRIMARY KEY, mode VARCHAR(16) NOT NULL DEFAULT 'all',
                            updated_by VARCHAR(64), updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP);
CREATE TABLE access_policy_orgs (org_id INTEGER PRIMARY KEY REFERENCES organizations (id),
                                 include_children BOOLEAN NOT NULL DEFAULT TRUE);

-- 身份审计扩展
ALTER TABLE audit_logs ADD COLUMN target_employee_id INTEGER;
ALTER TABLE audit_logs ADD COLUMN result VARCHAR(16);        -- success / failed
ALTER TABLE audit_logs ADD COLUMN reason_code VARCHAR(32);   -- 失败原因码
-- 菜单种子：employees「员工管理」（默认仅超管可见）
```

设计要点：

1. **绑定关系放在员工表单列 `bound_user_id`**（UNIQUE），不另建绑定表：`users.openid` 已 UNIQUE，两个唯一约束共同保证「一员工一微信、一微信一员工」，没有双份互相矛盾的身份数据。
2. **`token_version` 放在员工表**（改造计划 8.2 建议放用户表，此处等效且更合适）：失效的根因都发生在员工侧（停用、离职、换绑）；换绑后新微信用户拿到的是新版本号，旧微信令牌立即失效。
3. **手机号唯一**：改造计划要求「不允许存在无法自动识别的匹配冲突」，用数据库 UNIQUE 兜底，导入时提前报冲突。离职员工保留手机号；如该号码被新员工使用，须管理员先修改旧档案（导入报错提示）。
4. **在职状态与账号状态分离**：`employment_status`（来自名册导入，离职）与 `access_status`（管理员手动停用）任一不满足即拒绝；二者变化都自增 `token_version`。
5. **组织外键**：`org_id NOT NULL REFERENCES organizations`；现有「删除组织」逻辑需增加「被员工引用则保留」。
6. **历史数据**：现有 users 及其业务数据不动；员工首次手机号绑定时绑定到其当前 openid 对应的 users 行，历史步数/答题/勋章/排行自动保留。（已确认：所有存量用户都必须重新完成绑定。）
7. **审计不落敏感值**：手机号只记脱敏（`138****1234`），不记 phoneCode、JWT、session_key、AppSecret。
8. 回滚：`DROP` 新表、`DROP COLUMN` 审计新列、删除菜单种子与 `schema_migrations` 登记（仅在未产生业务数据前执行）。

## 5. API 变更方案

### 5.1 小程序侧（camelCase）

| 接口 | 鉴权 | 说明 |
|---|---|---|
| `POST /api/auth/login`（沿用路径，即改造计划的 wechat-login） | 公开 | 入参不变 `{code}`。后端 code2session 取 OpenID → 查绑定：<br>• `accessStatus=ok`：返回**业务令牌**（含 tv）+ user；<br>• `unbound`：返回**入驻令牌**（typ=onboard，10 分钟，仅可调绑定接口）；<br>• `disabled` / `resigned` / `org_denied`：不签发业务令牌，返回状态与提示。<br>前端永远不提交 OpenID |
| `POST /api/auth/bind-phone` | 入驻令牌 | `{phoneCode, scene}`：限流 → 校验入驻二维码 scene 有效 → 调微信换手机号 → 名册唯一匹配 → 在职/启用/组织准入/双方未绑定校验 → **事务内条件更新绑定** → 审计 → 返回业务令牌。重复点击：同一用户已绑定同一员工时幂等返回 |
| `GET /api/auth/binding-status` | 业务令牌或入驻令牌 | 返回 `{accessStatus, employee:{name, orgName}}`，启动时校验本地令牌用 |
| 全部业务接口 | 业务令牌 | `get_current_user` 每次实时查库判定；失败统一 `{"detail": 提示, "code": 原因码}`：<br>401 `token_invalid` / `token_revoked`（前端静默重登）；403 `unbound` / `disabled` / `resigned` / `org_denied`（前端清令牌跳提示页） |
| `WS /api/ws/updates` | 业务令牌 | 建连时同样做准入判定，失败 4403 |
| `GET /api/org/children` | 改为需业务令牌 | 去掉匿名浏览组织树 |
| `POST /api/org/select` | 业务令牌 | 已绑定员工返回 400「所属组织由管理员维护」 |

错误/原因码：`unbound`、`phone_not_in_roster`、`phone_conflict`、`resigned`、`disabled`、`org_denied`、`employee_bound_other`、`openid_bound_other`、`phone_code_invalid`（凭证无效/过期/已使用）、`wx_unavailable`（微信服务异常，可重试，**绝不放行**）、`onboard_qr_invalid`、`rate_limited`、`token_revoked`。

### 5.2 管理后台（snake_case，菜单 `employees`）

| 接口 | 说明 |
|---|---|
| `GET /api/admin/employees` | 分页；筛选：关键字（姓名/编号/手机号后 4 位）、组织（含下级）、在职状态、账号状态、绑定状态、准入结果；手机号**脱敏**返回 |
| `GET /api/admin/employees/{id}` | 详情 + 身份审计记录 |
| `PUT /api/admin/employees/{id}` | 编辑姓名/组织（调岗即时影响准入）/手机号（**不改变已有绑定**，记审计） |
| `PATCH /api/admin/employees/{id}/status` | `{access_status | employment_status, reason}`；停用/离职须原因，tv 自增 |
| `POST /api/admin/employees/{id}/unbind` | 换绑处理：解除当前微信绑定（须原因），员工用新微信重新扫码验证 |

| `POST /api/admin/employees/import-preview` | 预览：新增 / 更新 / 无变化 / 异常 四类统计 + 错误明细（前端导出错误报告 CSV） |

| `GET/POST /api/admin/onboarding-qrcode`、`POST .../revoke` | 查看当前二维码（图片可重复下载）、生成/重新生成（选择有效期或长期）、撤销 |

| `GET /api/admin/identity-audit-logs` | 身份类审计（绑定成功/失败、停用、启用、离职、换绑、导入、改手机号、策略变更、二维码），支持员工/动作/结果/日期筛选 |

## 7. 安全风险与兼容性风险

### 安全
1. **现状即高风险**：任何微信用户可直接调用全部业务接口 → 本次以统一依赖 + 实时查库消除；闭环测试枚举全部路由验证。
2. **二维码外泄**：二维码只是入口，绑定仍须手机号在名册内唯一匹配 + 准入通过；撤销二维码只阻止新入驻，不影响已绑定员工。
3. **手机号被他人使用**：微信手机号快速验证依赖微信侧手机号已验证；风险在于员工手机号转让/他人代绑 → 由「员工已绑定其他微信」拒绝 + 管理员换绑流程兜底，所有绑定记审计。
4. **令牌**：业务令牌 7 天，但每次请求比对 tv 与员工状态，停用即时失效；入驻令牌 10 分钟且只能用于绑定接口。
5. **微信服务异常**：任何换号失败一律拒绝绑定（返回可重试的 `wx_unavailable`），不降级放行。
6. **限流**：`bind-phone` 按 IP + 用户双维度限流；现有限流为进程内实现，多 worker 部署需换 Redis（遗留风险）。
7. **敏感信息**：手机号脱敏展示/审计，phoneCode、JWT、session_key、AppSecret 不写日志。`WX_SECRET` 仍只放本地 `.env`（历史泄露的密钥须在公众平台重置）。
8. **组织管理员数据范围**：改造计划要求「组织管理员只能操作授权范围内的人员」，现 RBAC 只有菜单级、无组织范围 → 需扩展（见第 9 章待确认）。

### 兼容
1. **存量用户全部需重新绑定**：上线后存量用户首次打开会进入入驻页，完成手机号验证后历史数据自动保留（绑定到原 users 行）。若存量用户名册内无其手机号，将无法进入——上线前须完成名册导入。
2. **组织选择流程下线**：组织由名册决定，`org-select` 引导与「修改组织」入口移除；`users.org_id` 由员工档案同步维护。
3. **PC 扫码登录（pages/bind）**：确认扫码需要业务令牌 → 微信关联管理员也必须是在册且准入的员工；超管账号密码登录不受影响。
4. **automator/e2e 脚本**：全部依赖 mock 登录 + 组织选择，需统一改为「造名册 + mock 手机号绑定」helper，否则全部失败。
5. **WebSocket**：小程序端 WS 建连需业务令牌，未准入用户不再建连。
6. **getPhoneNumber 在开发者工具**：真实 code 需真机或已认证账号，开发者工具联调使用 mock 开关；**最终验收必须真机**。

## 9. 需要确认的事项

1. **微信平台能力**：小程序是否为已认证的非个人主体？是否同意按 0.03 元/次购买手机号验证资源包（1000 次免费后）？——此项只能在微信公众平台核实，若不满足按第 6 章替代方案处理。
2. **入驻二维码是否作为绑定必要条件**：建议「必须」（撤销/过期二维码即可关闭新入驻窗口；员工从搜索、最近使用进入小程序时也会提示扫码）。
3. **组织管理员数据范围**：建议本次同步实现「后台角色可限定组织范围（含下级），员工管理接口按范围过滤与校验」，超管不受限。
4. **默认昵称**：员工首次绑定时，若昵称仍为默认「长征小战士」，建议自动设为员工姓名（仍保留一次改名机会）。

## 10. 确认结果与方案调整（2026-10-11，以本章为准）

| 事项 | 确认结果 | 方案调整 |
|---|---|---|
| 微信平台能力 | **不满足**手机号快速验证条件 | 不接入 `getPhoneNumber`，也不以手动输入手机号代替；采用第 6 章替代方案②：**管理员一次性绑定码**。为满足「管理员不逐个生成和分发」，绑定码支持**按筛选条件批量生成并导出 Excel**（员工编号/姓名/脱敏手机号/绑定码/有效期），由管理员经内部渠道一次性下发；明文只在生成当次返回/导出，库内仅存 SHA-256 摘要 |
| 入驻二维码 | **只作入口** | 不建 `onboarding_qrcodes` 表、不校验 scene；后台「入驻二维码」生成指向 `pages/onboard/onboard` 的固定小程序码供查看/下载。该码不授予任何权限，无需撤销；准入始终以绑定码 + 员工状态 + 组织准入为准 |
| 组织管理员数据范围 | **本次实现** | 新增 `admin_role_orgs(role_id, org_id, include_children)`；角色未配置组织 = 不限范围；管理员的范围 = 启用角色范围并集（任一启用角色不限即不限），超管不限。员工列表/详情/编辑/状态/换绑/绑定码/导入均按范围过滤与校验（越权返回 403 并审计）；准入策略、入驻二维码等全局配置仅不限范围的管理员可改 |
| 默认昵称 | **保持原昵称** | 绑定不修改 users.nickname |

### 10.1 调整后的首次入驻流程

扫入驻二维码（或直接打开小程序）→ `wx.login` → `POST /auth/login`：未绑定返回入驻令牌 → 入驻页输入绑定码 → `POST /auth/bind`（限流；码有效/未用/未过期 → 员工在职/启用/组织准入 → 员工未绑定、当前微信未绑定 → 同一事务核销绑定码 + 绑定）→ 返回业务令牌 → 直接进入首页。之后再次打开按第 7 章场景 A~F 自动恢复登录，无需再次输入绑定码。

### 10.2 数据库变更调整（012）

- `employees`：同第 4 章（手机号保留为名册必填字段，格式校验 + 唯一，用于管理员核对与线下下发绑定码，不参与自动匹配）。
- `employee_bind_codes`：`employee_id`、`code_hash`(UNIQUE)、`status`(active/used/revoked)、`expires_at`、`batch_id`、`created_by`、`used_at`、`used_by_user_id`、`revoked_at`；重新生成或停用/离职时旧码立即撤销。
- `access_policy` / `access_policy_orgs`：同第 4 章；按组织模式下允许组织为空时一律拒绝。
- `admin_role_orgs`：组织数据范围。
- `audit_logs`：`target_employee_id`、`result`、`reason_code`。
- 删除第 4 章 `onboarding_qrcodes`。

### 10.3 API 调整

- `POST /api/auth/bind-phone` → **`POST /api/auth/bind {bindCode}`**（入驻令牌）。原因码去掉 `phone_*`、`wx_unavailable`（绑定不再依赖微信服务端），新增 `bind_code_invalid`（不区分不存在/已用/已撤销/已过期）。
- 管理端新增 `POST /api/admin/employees/{id}/bind-code`（单个生成）、`POST /api/admin/employees/bind-codes/export`（批量生成并下载 Excel）、`POST /api/admin/employees/{id}/bind-code/revoke`；入驻二维码改为 `GET /api/admin/onboarding-qrcode`（只读生成）。
- 第 6 章手机号相关配置、费用、`WX_PHONE_MOCK` 不再需要；`stable_token` 改造仍保留（小程序码使用）。
